# FlowFit — Domain Distillation

## Scope & Method

Sources read as priors: `context/foundation/prd.md`, `context/foundation/tech-stack.md`,
`context/foundation/roadmap.md`, `context/foundation/idea-notes.md`, `context/foundation/lessons.md`,
`src/types.ts`, all `supabase/migrations/*.sql`, all `src/lib/services/*.ts`, `src/lib/validation/*.ts`,
the API routes under `src/pages/api/`, `src/middleware.ts`, and the Astro/React pages/components that
render plan, session, and history data. A PRD exists and is treated as authoritative for intent;
code is treated as authoritative for what actually runs. No extended narrative/history document beyond
the PRD and the roadmap's "Done"/"Parked" sections was found, so intentionality claims below lean on
those two documents plus in-code comments (several migrations carry unusually rich "why" comments from
prior code review, which are cited directly).

Every claim below cites a source (`file:line`) or is marked **BRAK w kodzie** (absent from code).

## KROK 5 — Refactor Ranking

Ranked by (value = how core the underlying invariant/behavior is) × (risk = how weakly it is enforced or how far it has drifted from the documented model today).

**#1 — `WorkoutSession` status-transition guard (KROK 3 §3, row 4 / KROK 4 not listed but same class as #3).**
Highest priority: this protects the **north star** flow (roadmap.md:24) — set logging integrity — and today the "must be active" rule lives only in three Astro route handlers, not the database. The fix pattern already exists verbatim in this codebase: `reset_user_profile` had the identical shape of bug (app-layer-only check, "racy... and fully bypassable") and was closed by moving the check into the RPC's own transaction (`supabase/migrations/20260723000000_reset_rpc_hardening.sql:6-14,62-66`). Applying the same pattern to session writes (either a `CHECK`/trigger, or routing all set/session mutations through a `SECURITY INVOKER` RPC that re-validates status) is a small, well-precedented, incremental change with a clear first step: add a status-aware `CHECK` or a guarding RPC for `workout_sets` inserts, mirroring the exact hardening already applied elsewhere in this schema.

**#2 — `exercises.tracking_type` column gap (KROK 4 #6).**
Not a design-quality issue but a correctness gap between the checked-in migrations and the type system/code that depends on them — worth investigating before any other refactor here, since every read of `Exercise.tracking_type` downstream (plan generation candidate selection, set-schema selection in `sets.ts:87`) is unverifiable from the repo alone.
