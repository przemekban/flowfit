# Roadmap: FlowFit

> Derived from `context/foundation/prd.md` (v1) + auto-researched codebase baseline.

> Slices below are listed in dependency order. The "At a glance" table is the index.

## Vision recap

Active people who care about their fitness lack a tool that delivers a genuinely personalized training plan without burdening them with manual configuration or choice paralysis. FlowFit fills the gap between "too simple" (step counters) and "too complex" (coach-grade tools) by generating a tailored weekly plan from a short onboarding survey — and then letting the user log their workout in real time against that plan. The product is viable when a first-time user can travel from registration to a saved workout history entry in a single session.

## North star

**S-03: user can launch a planned session and log sets, reps, and weight in real time** — the north star (the smallest end-to-end flow that, if working, proves the product hypothesis is real and the user experience is sound) is the workout logging screen, not the AI plan itself; a plan that generates correctly but is painful to act on is still a failed product.

## Foundations

### F-01: Core database schema and exercise library

- **Outcome:** (foundation) `user_profiles`, `exercises`, `planned_sessions`, `workout_sessions`, and `workout_sets` tables created in Supabase with per-operation RLS policies; exercise library seeded with categorized data by the developer.
- **Change ID:** core-db-schema
- **PRD refs:** NFR (data persistence guardrail: "workout data must be persistent after a session is saved"; data isolation guardrail: "each user's data is strictly isolated"), FR-007
- **Unlocks:** S-01 (needs `user_profiles` to store survey answers), S-02 (needs `exercises` + `planned_sessions` for AI plan storage), S-03 (needs `workout_sessions` + `workout_sets` for logging), S-04 (needs `workout_sessions` to query history)
- **Prerequisites:** —
- **Parallel with:** —
- **Blockers:** —
- **Unknowns:** —
- **Risk:** all user-facing slices block on this foundation; if the schema design is wrong (incorrect FK structure, missing indexes for history queries, or RLS policy gaps), every downstream slice inherits the problem — worth a design pass on table relationships and index strategy before writing the migration.
- **Status:** ready

## Slices

### S-01: Onboarding survey

- **Outcome:** user can complete the one-time onboarding survey (training goal, experience level, equipment, preferred style, sessions per week) and see their training profile saved.
- **Change ID:** onboarding-survey
- **PRD refs:** FR-001, FR-002, FR-003, FR-004, FR-005, US-01
- **Prerequisites:** F-01
- **Parallel with:** —
- **Blockers:** —
- **Unknowns:** —
- **Risk:** auth (FR-001–003) is already in the baseline; the risk here is survey routing — if the app does not correctly gate the survey behind auth and redirect to the plan page after completion, the primary user flow breaks at the very first step.
- **Status:** proposed

### S-02: AI plan generation

- **Outcome:** user can see their personalized weekly training plan (N sessions, each with an ordered exercise list matched to their profile) generated by AI from their survey answers.
- **Change ID:** ai-plan-generation
- **PRD refs:** FR-006, FR-007, US-01
- **Prerequisites:** F-01, S-01
- **Parallel with:** —
- **Blockers:** —
- **Unknowns:**
  - Which AI provider: Anthropic SDK directly vs OpenRouter? (`tech-stack.md` lists both as candidates; integration approach, model selection, pricing, and streaming support differ between them.) — Owner: team. Block: yes.
- **Risk:** the AI call is the highest-risk technical component — latency may exceed 2s (NFR requires continuous visible progress feedback), the response must be parsed into structured plan data, and Cloudflare Workers' free-tier 10ms CPU ceiling may trigger a silent 1101 error if Zod validation and SSR rendering run in the same isolate; see `infrastructure.md` risk register for mitigations.
- **Status:** blocked

### S-03: Workout session logging

- **Outcome:** user can launch a planned session from their weekly plan and log sets, reps, and weight for each exercise in real time — data persisted without requiring a separate explicit save action.
- **Change ID:** workout-session-logging
- **PRD refs:** FR-008, FR-009, FR-010, US-02
- **Prerequisites:** F-01, S-02
- **Parallel with:** —
- **Blockers:** —
- **Unknowns:** —
- **Risk:** this is the north star — if the logging UX has too many taps, the product's core promise of zero friction is broken; the acceptance criterion "input reachable in at most two taps from the active exercise" is load-bearing and must be verified on a real device or browser before calling this done.

## Open Roadmap Questions

1. **OQ-001 — Profile update mechanism:** If a user's training goal or available equipment changes after the onboarding survey, the current plan becomes outdated. A minimal "reset profile and retake survey" option may be needed before the product is viable for users beyond the initial developer-test phase. Owner: product. Block: no (does not gate any roadmap item for MVP; affects post-launch viability for external users).

2. **ORQ-2 — AI provider choice:** `tech-stack.md` lists both Anthropic SDK directly and OpenRouter as candidates for FR-006. The integration approach differs across model selection, pricing, streaming support, and error handling. Owner: team. Block: S-02.
