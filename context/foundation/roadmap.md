# Roadmap: FlowFit

> Derived from `context/foundation/prd.md` (v1) + auto-researched codebase baseline.

> Slices below are listed in dependency order. The "At a glance" table is the index.

## Vision recap

Active people who care about their fitness lack a tool that delivers a genuinely personalized training plan without burdening them with manual configuration or choice paralysis. FlowFit fills the gap between "too simple" (step counters) and "too complex" (coach-grade tools) by generating a tailored weekly plan from a short onboarding survey — and then letting the user log their workout in real time against that plan. The product is viable when a first-time user can travel from registration to a saved workout history entry in a single session.

## North star

**S-03: user can launch a planned session and log sets, reps, and weight in real time** — the north star (the smallest end-to-end flow that, if working, proves the product hypothesis is real and the user experience is sound) is the workout logging screen, not the AI plan itself; a plan that generates correctly but is painful to act on is still a failed product.

## Foundations

### F-01: Core database schema and exercise library

- **Outcome:** (foundation) Eight tables created in Supabase with per-operation RLS policies: `user_profiles`, `exercises`, `workout_templates`, `workouts`, `workout_exercises`, `user_plan`, `workout_sessions`, `workout_sets`. Exercise library seeded with categorized data by the developer. `workout_templates` table created but not seeded (template library seeding deferred to post-MVP when the browser UI is built). TypeScript entity and DTO types written to `src/types.ts`.
- **Change ID:** core-db-schema
- **PRD refs:** NFR (data persistence guardrail: "workout data must be persistent after a session is saved"; data isolation guardrail: "each user's data is strictly isolated"), FR-007
- **Table roles:**
  - `user_profiles` — survey answers per user (editable in V2)
  - `exercises` — developer-seeded exercise library; read-only for users
  - `workout_templates` — developer-seeded workout blueprints; read-only for users (V2 browseable)
  - `workouts` — user-owned workout copies: AI-generated or cloned from templates; editable in V2
  - `workout_exercises` — ordered exercise list within a user workout (target sets/reps)
  - `user_plan` — ordered rotation of a user's workouts (position 1…N, N = sessions_per_week)
  - `workout_sessions` — actual logged workout event (FK → workouts)
  - `workout_sets` — individual set log rows (exercise, reps, weight) within a session
- **Unlocks:** S-01 (needs `user_profiles`), S-02 (needs `exercises` + `workouts` + `workout_exercises` + `user_plan` for AI plan storage), S-03 (needs `workout_sessions` + `workout_sets` for logging), S-04 (needs `workout_sessions` to query history)
- **Prerequisites:** —
- **Parallel with:** —
- **Blockers:** —
- **Unknowns:** —
- **Risk:** all user-facing slices block on this foundation; if the schema design is wrong (incorrect FK structure, missing indexes for history queries, or RLS policy gaps), every downstream slice inherits the problem — worth a design pass on table relationships and index strategy before writing the migration. Index on `workout_sessions(user_id, completed_at)` is load-bearing for S-04 history queries and must be included here.
- **Status:** done

### S-02: AI plan generation

- **Outcome:** user can see their personalized weekly training plan (N sessions, each with an ordered exercise list matched to their profile) generated by AI from their survey answers.
- **Change ID:** ai-plan-generation
- **PRD refs:** FR-006, FR-007, US-01
- **Prerequisites:** F-01, S-01
- **Parallel with:** —
- **Blockers:** —
- **Unknowns:**
  - ~~Which AI provider: Anthropic SDK directly vs OpenRouter?~~ Resolved (ORQ-2): originally Anthropic, reversed 2026-07-10 to Google Gemini (free tier) — see `tech-stack.md` ORQ-2 revision history.
- **Risk:** the AI call is the highest-risk technical component — latency may exceed 2s (NFR requires continuous visible progress feedback), the response must be parsed into structured plan data, and Cloudflare Workers' free-tier 10ms CPU ceiling may trigger a silent 1101 error if Zod validation and SSR rendering run in the same isolate; see `infrastructure.md` risk register for mitigations.
- **Known limitation (found during implementation, 2026-07-10):** if a user's onboarding equipment/experience selection is too narrow to yield the minimum 4 exercises the plan generator needs (e.g. selecting only `resistance_band`), generation fails with a clear error — but the only recovery offered is the generator's "Try again" retry button, which will fail identically every time since nothing about the request changes. There is no in-MVP way for the user to go back and broaden their equipment selection (see OQ-001 — no profile editing/retake in MVP). Deferred; needs a decision (e.g. surface a more specific "not enough exercises for your equipment" message with a link back to onboarding, or a minimal retake-survey affordance) before this can bite a real user. See `context/changes/ai-plan-generation/plan.md` (Progress 3.4) and `context/changes/ai-plan-generation/research.md` (Follow-up Research) for the discovery.
- **Status:** blocked

## Open Roadmap Questions

1. **OQ-001 — Profile update mechanism:** If a user's training goal or available equipment changes after the onboarding survey, the current plan becomes outdated. A minimal "reset profile and retake survey" option may be needed before the product is viable for users beyond the initial developer-test phase. Owner: product. Block: no (does not gate any roadmap item for MVP; affects post-launch viability for external users).
   - **Concrete failure mode found in S-02 (2026-07-10):** a too-narrow equipment/experience selection can leave too few candidate exercises to ever generate a plan (verified: `resistance_band`-only equipment matches just 1 exercise in the seeded catalog). Today the user is stuck with a "Try again" button that will always fail the same way — this is the sharpest concrete case for why OQ-001 matters, not just a hypothetical. See S-02's "Known limitation" note above.

2. ~~**ORQ-2 — AI provider choice**~~ Resolved: originally Anthropic SDK direct, reversed same-day (2026-07-10) to Google Gemini (free tier) — Anthropic's API is not free and the project needs a $0 provider. See `tech-stack.md` ORQ-2 revision history.

- **Social features** — Why parked: PRD §Non-Goals; the product is private and single-user in its social model.

- **Workout template library browser** — Why parked: PRD §Non-Goals; `workout_templates` table created in F-01 for architectural readiness; browsing/copying UI is V2.

- **Workout-first navigation (V2)** — Why parked: MVP entry point is the plan page; workout list with "suggested next" rotation is the V2 navigation model. The `user_plan` table created in F-01 supports the rotation logic when the UI is built.
